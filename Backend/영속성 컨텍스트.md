### 작동 원리
* db에서 엔티티를 가져오거나 저장할 때 그 엔티티가 영속성 컨텍스트에 저장된다.
* 여기서 우리는 repository로 간단하게 작업이 가능하지만, 실제 그 작업을 실행하여 영속성 컨텍스트에 저장하는 것은 entitymanager이다.
### 엔티티 생명 주기
	1. 비영속 : 영속성 컨텍스트에 들어있지 않은 상태
	2. 영속 : 영속성 컨텍스트에 들어있는 상태.
	3. 삭제 : 삭제된 상태. 
	4. 준영속 : 원래 영속성 컨텍스트에 있었는데 분리된 상태


비영속 상태는 People people = new people("곽효오") 처럼 직접 생성한 객체와 같이 db에 안 반영되는 애들이 속하는 상태이다.

영속 상태는 그와 반대로, repository 메서드와 같이 db 서버에서 가져왔거나 저장한 엔티티가 속한다.

준영속 상태는 영속성 컨텍스트에 들어있던 놈이 잠시 분리되면 속하는 상태이다. ex)em.detach(people)

삭제는 영속성 컨텍스트 안에 있으면서 flush 때 삭제가 예약된 엔티티가 속하는 상태이다.

참고로 `flush`는 한마디로:

> **영속성 컨텍스트에 쌓여 있던 변경사항을 DB에 SQL로 보내서 동기화하는 것** 이라 한다.

### 얻는 이점
### 1. 1차 캐시
1차 캐시가 뭐냐면 영속성 컨텍스트 내부에 있는 캐시로, 엔티티 매니저와 db 사이의 매개체 역할을 한다. db에서 가져오면 오래 걸리는데 그걸 반복하는 대신 영속 상태의 엔티티들은 영속성 컨텍스트에서 가져올 수 있어서 훨씬 효율적이다.
1차 캐시에 저장된 엔티티들은 식별자로 가져와 접근할 수 있다.

### 2. 동일성 보장

1차 캐시에서 동일한 id를 가진 엔티티를 두 개를 조회해서 가져온 다음, == 연산자로 주소 값을 비교해 보면 같다고 나온다. 이는 동일성을 보장한다.

### 3. 트랜잭션을 지원하는 쓰기 지연

말만 들으면 어려워 보이는데
그냥 트랜잭션 안에서 em이 영속성 컨텍스트에 있는 엔티티를 수정한다 하면,
바로 수정하는 게 아니라 커밋 될 때까지 쿼리 저장소에 저장하며 기다렸다가 한번에 쿼리를 db에 날리는 것이다.

### 4. dirty checking
다음은 백엔드라면 한 번 쯤 들어봤을 더티 체킹이다. 
작동 원리는 영속성 컨텍스트에 진입할 때 스냅샷을 찍어 두고 flush가 될 때 엔티티의 변경 사항을 스냅샷과 비교하여 변경된 부분은 수정 쿼리를 작성해 쿼리 저장소에 저장한다.
